## 1. 项目用途和主要功能

TraceTrackCar 是一个以 **STM32F407ZG** 为主控制器的循迹小车项目。项目采用分层结构，将芯片外设、器件驱动、算法和整车应用分开，目标是完成小车底盘控制、灰度循迹、姿态与航向估计、距离测量、路线状态机、显示和视觉模块通信等功能。

代码中已经实现的主要能力如下：

- 支持两轮驱动（2WD）和四轮驱动（4WD）两种硬件配置；当前默认是 **2WD**。
- 电机方向与 PWM 输出控制。
- 最多四路正交编码器采集，以及转速、累计计数和里程换算。
- 底盘控制权仲裁、差速目标分配、目标斜坡、各驱动轮独立的PWM前馈＋PI速度闭环，以及编码器无反馈、方向错误和命令租约超时锁存停车；可通过宏退回固定前馈开环排障。
- 直行指定距离、原地转动指定角度的非阻塞动作接口。
- 8 路灰度传感器采集、黑线判断、位置误差计算和 PD 循迹。
- 支持两种灰度传感器来源：带 MCU 的 I2C 模块和 74HC4051 模拟多路复用模块；当前默认使用 **MCU-I2C 灰度模块**。
- ICM-20948 九轴 IMU 采集、陀螺仪静止标定、姿态融合和航向输出。
- VL53L1X ToF 前向测距。
- HX711 称重 ADC 非阻塞采样、去皮、砝码标定和克重缓存读取。
- 当前提供 **Basic 基础路线**，并保留可扩展的编译期赛道方案选择接口。
- 1.54 英寸 240×240 SPI TFT LCD 和 128×64 I2C OLED 显示。
- USART1 可通过宏选择普通直连串口或 E220 无线透明串口；E220 模式带完整帧软件队列和 AUX 空闲重试，USART2 保持为 K210 通信接口。
- K210可变数量数字识别结果已能通过USART2稳定发送到STM32；STM32完成固定7字节帧校验、完整快照组装、缓存、在线判断和错误统计，基础数字通信已实测通过。
- 基于静态任务表的非阻塞协作式调度器，不依赖 RTOS。

### 1.1 任务表使用原则

`APP/app_task_config.h`中的任务表按测试目的切换。本文不记录调试期间的当前注册状态；稳定的任务组合、周期和按键说明统一见`Doc/测试任务注册函数使用方法.md`。所有任务表必须保留`Test_GPIO_Toggle`和`AppTask_BSP_Background`，使用按键时先注册`Key_Update`，使用LCD/OLED专用页面时还需注册对应的`LCD_Update`/`OLED_Update`刷新任务。

## 3. 主要模块及其功能

### 3.1 BSP 板级支持层

| 模块 | 文件 | 功能 |
| --- | --- | --- |
| 统一初始化 | `BSP/bsp_all.c` | 依次初始化 SysTick、GPIO、PWM、编码器、ADC、按键、EXTI、UART、I2C 和 SPI |

| GPIO | `BSP/bsp_gpio.*` | 电机方向、LCD 控制、IMU 片选、4051 选通、HX711、激光使能和 E220 AUX 等普通 GPIO |

| 按键/外部中断 | `BSP/bsp_key.*`、`BSP/bsp_exti.*` | 五个低电平按键和通用 EXTI 模板 |

### 3.3 Algorithm 算法层

| 模块 | 作用 |
| --- | --- |
| `pid.*` | 通用PID，支持外部前馈、输出/积分限幅和饱和方向暂停积分 |

| `line_track.*` | 对灰度误差做滤波和 PD 计算，生成线速度与转向速度 |

### 3.4 APP 应用层

| 模块 | 作用 |
| --- | --- |
| `app_all.*` | 统一初始化底盘、里程、姿态、航向、动作、传感器、循迹、显示和 K210 协议层 |
| `scheduler.*` | 遍历静态任务表，按毫秒周期调用各个非阻塞 `Update` 函数 |
| `app_task_config.h` | 当前实际运行的任务列表、任务顺序和周期配置入口 |
| `chassis.*` | 底盘控制权仲裁、左右差速目标分配、目标斜坡、每个启用驱动轮的前馈＋PI速度控制，以及编码器/命令租约故障锁存停车 |
| `motion_action.*` | 非阻塞直行距离和转动角度动作，并负责申请、停止和释放动作控制权 |

| `line_follow_app.*` | 灰度采集、线检测、路线决策和底盘输出的应用入口 |

| `nb_wait.*` | 通用非阻塞等待辅助模块 |

### 3.5 Route 路线层

- `route_manager.*` 只向选中的赛道实现转发线路输入、动作反馈和控制意图，不直接调用 APP、Motion 或底盘。
- `route_profile_select.*` 根据 `ROUTE_PROFILE_SELECT` 把统一的 `RouteProfile_*` 接口转发到具体赛道实现；未知编号会在编译期报错。
- `route_profile_basic.*` 只进行普通循迹。
- `route_common.h` 定义每周期控制意图、动作请求/反馈和统一赛道状态快照；真正的底盘控制权由 APP 层仲裁。

### 3.6 K210 侧

- K210实际运行的Python识别程序和模型保存在SD卡，当前未纳入本仓库；SD卡根目录`main.py`负责上电自动启动识别程序。
- 已通过测试的K210程序使用IO6作为UART1_TX，以115200、8N1向STM32发送BEGIN/ITEM/END数字快照；结果在K210侧按画面横坐标从左到右排序。
- STM32的`APP/k210_comm.*`已与SD卡运行版本完成协议联调。完整协议、SD卡路径、接线、日志和验收方法见[《K210数字识别与STM32通信说明》](K210数字识别与STM32通信说明.md)。

## 4. 程序运行流程

### 4.1 上电初始化流程

```text
复位/上电
  ↓
SystemInit()
  ↓
BSP_InitAll(SystemCoreClock)
  ├─ SysTick
  ├─ GPIO / PWM / 编码器 / ADC / 按键 / EXTI
  └─ UART / I2C / SPI
  ↓
Driver_Init()
  ├─ 电机
  ├─ 灰度传感器
  ├─ VL53L1X
  ├─ ICM-20948
  ├─ LCD
  └─ OLED
  ↓
App_Init()
  ├─ 底盘、里程、姿态、航向、动作
  ├─ 传感器管理、循迹和路线
  ├─ LCD/OLED 启动页
  └─ K210 协议状态
  ↓
Scheduler_Init()
  ↓
进入永久主循环
```

### 4.2 主循环与调度

`user/main.c` 的永久循环依次执行：

1. `BSP_UART_TaskAll()`：维护 UART 后台状态。
2. `Scheduler_Run()`：检查静态任务表中每个任务是否到期，到期则调用一次。

这是协作式调度，不是 RTOS：

- 所有任务必须快速返回，不能使用长时间 `delay`、阻塞式等待或无限等待循环。
- 如果某任务执行过久，其后的所有任务都会被推迟。
- 修改任务周期、顺序或启停状态时应改 `APP/app_task_config.h`，不应修改 `scheduler.c`。

### 4.3 动作库按键测试的数据流（使用对应任务表时）

```text
KEY1～KEY5 GPIO
  ↓ Key_Update（扫描、消抖、生成事件）
  ↓ Test_MotionCmd_Update
  ├─ KEY1 / KEY2：Motion_TurnAngle(±90)
  ├─ KEY3 / KEY4：Motion_GoDistance(±500, 800)
  └─ KEY5：Motion_Stop
  ↓ Encoder_Update（原始测速＋低通滤波）
  ↓ Motion_Update
  ↓ Chassis_Update
PWM前馈＋各驱动轮PI修正
  ↓
Motor_SetAllPermille
  ↓
PWM + 方向 GPIO
```

当前动作测试任务表下的按键控制：

| 输入 | 动作 |
| --- | --- |
| KEY1（PE4）按下 | 左转90°，统一转向速度上限3000 cps；IMU未准备好时拒绝 |
| KEY2（PE3）按下 | 右转90°，统一转向速度上限3000 cps；IMU未准备好时拒绝 |
| KEY3（PE2）按下 | 前进500 mm，速度800 cps |
| KEY4（PE1）按下 | 后退500 mm，速度800 cps |
| KEY5（PA15）按下 | 立即取消当前动作并停车 |

`Key_Update()`是独立的按键扫描任务，必须以10 ms周期注册在`Test_MotionCmd_Update()`之前。命令任务只读取稳定按下沿事件，按住按键不会连续触发。动作测试中不要同时注册`Test_Key_Update()`，否则两个任务会共同消费按键事件。是否显示页面取决于所选测试任务示例中是否注册`LCD_Update()`或`OLED_Update()`。

### 4.4 完整循迹流程（代码已实现，需切换到循迹任务表）

```text
Sensor_Update
  ↓ 灰度缓存
LineTrack_Update → LineFollow_Update
  ↓
LineDetect_Update（阈值、mask、线型、误差）
  ↓
RouteManager_Update
  ├─ 普通路段：返回循迹输出 → APP 持有循迹控制权并调用 Chassis_SetSpeed
  └─ 路线动作：返回动作请求 → APP 释放循迹控制权并启动 Motion
  ↓
Chassis_Update
  ↓
电机输出
```

以后新增会发起定距或定角动作的赛道方案时，任务表必须保留`Motion_Update`，否则动作请求不会继续推进；Basic路线本身不会发起动作。

## 5. 硬件连接和使用方法

### 5.1 使用前的基本原则

- 以下引脚以当前源码为准，默认配置为 `VEHICLE_DRIVE_MODE_2WD`。
- 所有外设与 STM32 必须共地。
- 电机电源、电机驱动板型号、驱动板逻辑电平、`STBY/EN/SLP` 有效电平和整车供电电压在现有资料中均未给出，属于 **待确认项**。
- 不要用 STM32 的 3.3 V 引脚直接给电机供电。电机应由与驱动板匹配的独立功率电源供电，并与控制板共地。
- 连接或调整电机、编码器、传感器前先断电；首次烧录和测试时将车轮悬空。

### 5.2 调试与通信接口

| 用途 | STM32 引脚 | 参数/接法 | 当前状态 |
| --- | --- | --- | --- |
| USART1 可选链路 TX | PA9 | 普通模式接 USB-TTL RX；E220 模式接 E220 RXD | 启用，当前配置为普通直连 |
| USART1 可选链路 RX | PA10 | 普通模式接 USB-TTL TX；E220 模式接 E220 TXD | 启用，当前配置为普通直连 |
| E220 AUX | PE6 | 接 E220 AUX，普通 GPIO 输入、无上下拉 | E220 模式启用；板级引出待确认 |
| USART1/E220 本地 GND | GND | STM32 与本地 E220 共地；电脑端 E220 与本地 USB-TTL 共地 | 两台远端 E220 之间不需要连接 GND |
| USART2/K210 TX | PA2 | 当前单向方案暂不接；保留给后续K210 RX | 启用 |
| USART2/K210 RX | PA3 | 接 K210 TX | 启用 |
| SWDIO | PA13 | 接 ST-Link SWDIO | 调试/烧录保留 |
| SWCLK | PA14 | 接 ST-Link SWCLK | 调试/烧录保留 |

USART1 和 USART2 当前均为 **115200、8 数据位、无校验、1 停止位、无硬件流控**。`BSP/vehicle_config.h` 的 `VEHICLE_UART1_LINK_MODE` 可选择 `VEHICLE_UART1_LINK_DIRECT` 或 `VEHICLE_UART1_LINK_E220`，当前源码选择`VEHICLE_UART1_LINK_DIRECT`，便于通过USB-TTL查看K210测试日志。切换到E220透明传输模式时，M0、M1必须可靠接低电平。

E220 AUX 是模块输出，可以悬空；不接时会失去忙/闲判断、上电就绪判断和发送缓存节流能力。切换到E220模式时，代码使用PE6读取AUX。AUX为低电平、USART1尚忙或UART TX空间不足时，`BSP_UART_WriteFrame()`会把完整帧复制到E220的16帧软件队列；`Drv_E220_Task()`在1 ms后台任务中等待AUX变高并按FIFO顺序重试。成功入队时接口返回`BSP_OK`，队列已满才返回`BSP_BUSY`。AUX高电平并不一定代表最后一包已经完成空中发送，具体还取决于固件版本和`AT+UAUX`配置。

115200 只表示 STM32 与 E220 之间的本地 UART 速率，不代表 LoRa 空口速率。无线发送间隔还会受到空中速率、子包长度、信号质量、重传/纠错、接收端显示方式和 `AT+UAUX` 配置影响，因此无线链路明显慢于普通串口属于正常现象。软件队列解决的是 AUX 忙时整帧被本机丢弃，不会提高物理空口吞吐。路线调试数据已转移到LCD/OLED，不再占用该链路。

AUX 是 3.3V 输出信号，不能接 3.3V/5V 电源强行拉高，也不能让 MCU 对该线输出高低电平。AUX 低电平可能来自上电/复位、模式切换、串口接收与断帧、模块缓存及无线收发过程。要提高发送速度，应让收发两端使用相同的更高 `AT+RATE`，并接受“速率越高、灵敏度和可靠距离越低”的取舍；较新固件可保持 `AT+UAUX=0`，避免 AUX 覆盖整个空中发送过程。模块 `VCC` 与 AUX 是完全不同的引脚，供电仍必须遵守模块规格。

普通模式和 E220 模式共用同一组 PA9/PA10，宏不会生成第二组物理串口。不要把 USB-TTL TX 与 E220 TXD 同时并接到 PA10；若必须同时连接两套设备，需要硬件切换/隔离或另选 UART。

当前通过测试的单向接线为：K210 IO6/UART1_TX→STM32 PA3/USART2_RX，两板GND相连；K210 RX和STM32 PA2/USART2_TX暂时不接。K210的供电方式和接口电平仍应以具体K210模块手册为准，不建议直接使用STM32开发板的3.3V引脚给K210供电。

注意：旧资料中曾出现 USART2 使用 PD5/PD6 的说明，但当前 `BSP/bsp_uart.h` 和 `APP/k210_comm.h` 明确使用 **PA2/PA3**，应以当前源码为准。

### 6.2 电机、编码器和底盘

`Chassis_SetSpeed()`接收`cps`形式的上层目标并进行左右差速分配。`Chassis_Update()`先以每10 ms最多200 cps的斜坡使实际控制目标跟随命令目标，再按`目标值×CONTROL_CHASSIS_PWM_MAX_PERMILLE/CONTROL_CHASSIS_FEEDFORWARD_FULL_SPEED_CPS`计算前馈，并用每个启用驱动轮的滤波编码器速度执行独立PI修正；最终输出统一限制在`±CONTROL_CHASSIS_PWM_MAX_PERMILLE`。停车、释放控制权和急停仍立即停止，目标方向反转时会复位相应PI状态。

速度闭环开启时，底盘会按启用车轮分别监控编码器无反馈和反馈方向错误。故障连续达到门槛后，底盘立即停车、释放控制权并锁存故障码与车轮掩码；锁存期间拒绝重新获取控制权和设置速度。修复原因并确认所有启用车轮原始速度绝对值不超过100 cps后，必须显式调用`Chassis_ClearFault()`。

速度模式的命令采用租约机制：当前控制权拥有者必须在默认200 ms内周期性调用`Chassis_SetSpeed()`。命令源停止刷新但`Chassis_Update()`仍运行时，底盘锁存`CHASSIS_FAULT_COMMAND_TIMEOUT`、以`mask=00`表示非车轮故障、立即停车并释放控制权。`Chassis_Info_t.command_age_ms`和测试日志的`age`字段用于观察最近一次有效命令的年龄；正常10 ms控制任务通常约为0～10 ms。

`CONTROL_LINE_DIRECTION_REVERSE`用于处理传感器整体安装方向：正常方向设为`0U`，将传感器在车上旋转180度后循迹左右相反时设为`1U`。该开关只规范化算法层方向，不改变Driver物理通道与逐路阈值的对应关系，因此不要手工倒序`LINE_DETECT_DEFAULT_THRESHOLD_0`～`_7`。`DRV_GRAY_MCU_INDEX_REVERSE`和`DRV_GRAY_4051_INDEX_REVERSE`属于驱动接线/通道排序配置，硬件接线未改变时不应与安装方向开关同时修改。

调参方向：

- `CONTROL_LINE_KP` 增大：纠偏更强，但过大可能蛇形振荡。
- `CONTROL_LINE_KD` 增大：更强调误差变化，但过大可能对灰度跳变敏感。
- `CONTROL_LINE_BASE_SPEED_CPS` 增大：速度更快，对传感器、机械和参数一致性要求更高。
- `CONTROL_LINE_TURN_MAX_CPS` 增大：普通纠偏更强；正常循迹仍会限制 `|turn| <= linear`，避免内侧轮意外反转。
- 丢线先连续确认2帧，再沿最后线路方向起扫；后续阶段交替方向并逐步增加扫描时间和转向量。重新看到线连续确认3帧后恢复PD，从首次丢线累计10秒仍未恢复则停车并保留`MODE:SAFE`诊断状态。

### 7.3 GNU Makefile 状态

根目录提供了 `Makefile` 和 GNU 链接脚本，但**当前不建议把它作为可靠的首选构建方式**，原因是脚本仍引用多个当前仓库不存在的源文件，例如：

- `user/bsp_led.c`
- `VL53L1_core/vl53l1_api.c`
- `VL53L1_core/vl53l1_api_calibration.c`

### 7.4 首次通电测试顺序

建议按“先底层、后控制、最后整车”的顺序测试：

1. **静态检查**：断电检查电源极性、共地、短路、驱动板使能、PWM/方向脚和编码器线。
2. **只接控制电源**：暂不接电机功率电源，烧录程序，确认 MCU 能运行，USART1 有输出。
3. **传感器初始化**：车辆保持静止，等待 IMU 完成陀螺仪标定；检查 I2C/SPI 设备在线情况。
4. **编码器方向**：手动正向转动车轮，确认对应编码器累计值方向正确、左右轮没有串线。
5. **开环电机**：低 PWM、车轮悬空测试每个电机的方向和急停。
6. **底盘速度内环和安全保护**：按`Encoder_Update → Test_ChassisCmd_Update → Chassis_Update`顺序注册任务，确认所有启用轮的原始/滤波反馈方向正确、斜坡后目标能跟踪命令且输出不持续饱和；随后分别验证无反馈、方向错误和命令停止刷新能在门槛时间后停车锁存，修复并停稳后才能清除。
7. **按键测试**：需要检查五个按键的独立按下/松开事件时，先切换到五按键专项任务表，再依次按下并松开 KEY1～KEY5，检查 USART1 是否输出对应引脚的 `PRESSED` 和 `RELEASED`。
8. **灰度标定**：确认 8 路数据顺序和黑白极性，再标定阈值。
9. **循迹测试**：先使用低速、简单闭合轨道；确认循迹任务表和`Chassis_Update`已注册后再落地运行；只有所选赛道方案会发起动作时才强制要求`Motion_Update`。
10. **路线与送药业务接入**：K210基础数字通信已经单独验证；接入正式路线时，继续测试送药状态机、基于数字结果的决策、舵机和激光，并保持通信层与车辆控制层分离。

## 8. 已知问题和注意事项

1. **任务表按测试目的切换。** 项目收尾前不在本文维护当前默认注册项；切换任务时以`Doc/测试任务注册函数使用方法.md`中的稳定示例为准，并检查任务顺序和显示刷新任务是否齐全。

2. **Makefile 仍不能代表当前完整工程。** 本机没有`make`命令，而且Makefile仍引用不存在的`user/bsp_led.c`、一组旧名`VL53L1_core/vl53l1_*.c`和`VL53L1_platform/vl53l1_platform_init.c`；Route源文件列表已与本轮删除和新增同步。已使用GNU Arm编译器对本轮修改的C文件逐个进行语法检查，结果为0错误，但没有完成全工程链接。最终烧录前仍应在Keil执行完整重编译。

3. **K210运行代码在SD卡中。** 当前仓库只保留STM32通信层，实际通过测试的K210 Python程序和模型没有纳入版本管理。修改模型、引脚、波特率或协议前必须先取得并核对SD卡运行版本，不能用旧示例替代；稳定协议和部署信息见`Doc/K210数字识别与STM32通信说明.md`。

4. **K210通信完成不等于送药业务完成。** 已验证的是数字识别、单向快照发送和STM32接收解析；正式送药任务状态机，以及根据数字执行停车、目标选择和路线动作的逻辑仍应放在独立业务模块中，不得写进UART中断、`bsp_uart.c`或`Test_K210_CommUpdate()`。

5. **当前只提供Basic赛道实现。** 已删除不再使用的HJduino实现；`ROUTE_PROFILE_SELECT`和`route_profile_select.*`继续作为后续赛道代码的编译期接入入口。

6. **当前Basic循迹已完成速度内环和丢线恢复回归测试。** 当前车辆和参数下循迹正常；更换轮胎、车重、灰度安装高度、电机、供电或新增赛道后仍需重新验证。基础版使用位置PD、按误差减速、两帧丢线确认、分阶段反向扩大搜索、三帧重新捕获和10秒安全停车。题目规定的主动离线段应由新赛道Route提前切换到Motion，不得全局关闭丢线保护。

7. **灰度标定不持久化。** 按KEY3后，LCD/OLED显示当前阈值，USART1打印八行可复制宏，但单片机不能直接修改电脑工程中的`#define`。若希望下次上电继续使用，需要人工更新`LINE_DETECT_DEFAULT_THRESHOLD_0`～`_7`，或另行实现Flash参数存储。

8. **项目资料已按当前源码校正。** 2026-07-21已同步K210数字识别通信的协议、IO6→PA3接线、SD卡代码边界、测试方法和实测结论；此前已同步底盘控制权边界、PWM前馈＋车轮速度PI、目标斜坡、编码器故障锁存与清除、命令租约看门狗、编码器速度滤波、分阶段丢线恢复、USART2、2WD/4WD、灰度、动作、路线和显示资料。当前仓库未发现Word原文件；若以后恢复Word文件，必须同步检查相关Markdown、Word和本文。

9. **2WD/4WD 会改变引脚资源。** 2WD 下 SPI1 使用 PA5/PA6/PA7，LCD 默认走 SPI1；4WD 下 PA6/PA7 用于后编码器，LCD 改走 SPI2 并与 ICM-20948 共线。切换驱动模式后必须重新核对全部接线，不能只改宏而不改硬件。

10. **IMU 标定期间必须静止。** Basic循迹不使用IMU，因此`LineFollow_Start()`不再因IMU未就绪而拒绝；`Motion_TurnAngle()`会在内部检查IMU初始化、数据有效、姿态有效和陀螺仪标定进度，条件不满足时返回`BSP_ERROR`且不会取得底盘控制权。使用定角动作前仍须保持车辆静止并等待IMU准备完成。

11. **磁力计会在电机活动时停用修正。** 当前 `ATTITUDE_MAG_DISABLE_WHEN_MOTOR_ACTIVE=1U`，用于降低电机磁干扰。磁标定参数与具体车辆安装位置有关，换车架、换电机或移动 IMU 后需要重新验证。

12. **LCD 缺少独立复位脚定义。** 当前只定义 CS、DC、BL 和 SPI 信号。实际 LCD 模块的 RST 是硬件上拉、与 MCU 复位相连还是需要额外 GPIO，现有资料无法确认。

13. **电机驱动使能和电源规格待确认。** 代码未定义独立 `STBY/EN/SLP` 控制，项目也没有提供电机驱动板原理图、额定电压、电流或保护方式。接电机功率电源前必须按实际硬件确认。

14. **舵机和激光目前主要是底层资源。** PF8/PF9 的 50 Hz PWM 和 PG2 激光使能已配置，但现有 APP/Route 代码中没有完整的目标跟踪、舵机限位和激光安全状态机。不要在未确认机械限位、脉宽和安全措施前驱动实物。

15. **共享总线需要整体测试。** 默认 I2C1 同时服务灰度模块、OLED 和 VL53L1X；4WD 时 SPI2 同时服务 IMU 和 LCD。代码采用非阻塞状态机与总线忙判断，但电气上拉、线长、设备兼容性和高负载下的时序仍必须在实机上验证。

16. **任务不能阻塞。** 调度器没有抢占能力。新增测试、日志或业务函数时，避免长延时、等待硬件完成的`while`循环和大量串口同步输出，否则会影响传感器采样、控制和安全停止响应。

17. **PC13、PE0、PE6、舵机和激光的实际板级连接待确认。** 代码层已确认 PE6 未被其他启用资源占用，并将其分配为 E220 AUX；但仓库中没有整车原理图或开发板引脚图，不能确认 PE6 是否已引出或连接板载器件。

18. **烧录前必须确认正在使用新产物。** `Objects` 和 `build` 中已有历史产物，时间和构建方式不同。每次修改参数或任务表后应执行干净重编译，并核对输出文件时间戳。

19. **E220 软件队列不是无限缓存。** 默认队列为 16 个完整帧、每帧最多 512 字节，约占 8 KiB RAM。若日志长期快于空口发送能力，队列最终仍会填满；可用 `Drv_E220_GetTxStats()` 检查 `queued_frames`、`queue_full_frames` 和 `oversize_frames`。`Drv_E220_ClearTxStats()` 只清统计值，不删除已排队帧。

20. **路线测试改用显示专用页面。** `Test_RouteLog`只激活LCD/OLED页面，不再发送USART1日志；LCD约每200 ms显示10行信息，OLED按自身刷新周期在A/B两页间自动切换，覆盖profile、状态、原始/滤波误差、丢线、搜索、控制输出和航向信息。

21. **编码器故障保护不能代替硬件诊断。** 速度闭环和保护均开启时，达到目标/PWM门槛后的持续低反馈或反向反馈会锁存故障并自动停车；但无反馈故障不能区分编码器断线、接头松动和机械堵转。触发后必须检查实物，修复并确认所有启用轮原始速度绝对值不超过100 cps后再调用`Chassis_ClearFault()`，不得通过关闭保护或反复清故障继续运行。

22. **软件命令租约不能代替整机硬件看门狗。** `CHASSIS_FAULT_COMMAND_TIMEOUT`只在`Chassis_Update()`仍被调度时发现上层速度命令停止刷新；如果主循环、调度器或MCU整体停止执行，软件无法主动更新电机输出。需要覆盖整机卡死时应另行启用硬件独立看门狗，并把喂狗位置设计为能反映关键任务健康状态。
