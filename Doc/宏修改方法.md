# 宏修改方法

> 本文按当前项目源码校正。当前 `Doc` 目录未发现对应的 Word 原文件；若后续恢复 Word 文件，必须同时检查本文和 `说明文档.md`。

## 零、启用专项测试代码：Test/test_config.h

```c
#define PROJECT_TEST_TASKS_ENABLE 0U
```

- `0U`：正式固件默认值，`Test/test.c`不生成任何`Test_*`任务代码，正式任务表使用`APP/app_diagnostics.*`。
- `1U`：启用专项测试；还需在`APP/app_task_config.h`中临时包含`Test/test.h`并注册需要的测试任务。
- 测试完成后必须恢复为`0U`并恢复正式任务表，避免测试命令、串口日志和硬件动作进入正式固件。

## 一、切换 USART1 普通串口/E220 无线串口：BSP/vehicle_config.h

```c
#define VEHICLE_UART1_LINK_DIRECT           0U
#define VEHICLE_UART1_LINK_E220             1U
#ifndef VEHICLE_UART1_LINK_MODE
#define VEHICLE_UART1_LINK_MODE             VEHICLE_UART1_LINK_DIRECT
#endif
```

- `VEHICLE_UART1_LINK_DIRECT`：USART1 保持普通直连串口，PA9/PA10 可接 USB-TTL 或其他 UART 设备，不使用 PE6。
- `VEHICLE_UART1_LINK_E220`：USART1 接 E220；PA9→E220 RXD、PA10←E220 TXD、PE6←E220 AUX。当前默认选择普通直连模式，需要无线链路时再改为此模式。
- 两种模式都使用 `BSP/bsp_uart.h` 中 USART1 的 115200、8N1、无硬件流控配置。
- E220 透明传输模式还要求 M0、M1 均可靠接低电平，不能悬空；本项目没有用 MCU 控制 M0/M1。
- PE6 在当前源码中没有其他用途，但实际开发板是否已将 PE6 引出、是否与板载器件复用仍为“待确认”。
- 该宏选择的是同一组 PA9/PA10 的软件行为与外部接线。不要把 USB-TTL TX 和 E220 TXD 同时并接到 PA10；需要同时保留两套物理设备时，应增加硬件切换/隔离或改用另一组 UART。

### （一）E220 软件帧队列

E220 模式的软件帧队列在 `Driver/drv_e220.h` 配置：

```c
#define DRV_E220_TX_QUEUE_DEPTH          16U
#define DRV_E220_TX_FRAME_MAX_SIZE       512U
```

- AUX 忙、USART1 忙或 UART TX 空间不足时，`BSP_UART_WriteFrame()` 会保存整帧，`Drv_E220_Task()` 等 AUX 变高后重试。
- 队列深度越大，能吸收的短时拥塞越多，但默认每增加一帧约增加 512 字节 RAM；不能靠无限增大队列解决持续带宽不足。
- `DRV_E220_TX_FRAME_MAX_SIZE` 不得大于 `UART_TX_BUF_SIZE`。

路线测试数据已改到LCD/OLED，不再进入E220队列。需要两块屏同时显示时使用以下完整任务组合：

```c
Task_t task_list[] = { \
{ Test_GPIO_Toggle,        10U, 0U }, /* 运行指示灯 */ \
{ AppTask_BSP_Background,   1U, 0U }, /* BSP和Driver后台维护 */ \
{ Key_Update,              10U, 0U }, /* 按键扫描 */ \
{ Sensor_Update,            1U, 0U }, /* 传感器状态机 */ \
{ Encoder_Update,          10U, 0U }, /* 编码器测速 */ \
{ Test_RouteCmd_Update,    10U, 0U }, /* 路线测试按键 */ \
{ LineTrack_Update,        10U, 0U }, /* 路线与循迹 */ \
{ Motion_Update,           10U, 0U }, /* 动作推进 */ \
{ Chassis_Update,          10U, 0U }, /* 底盘速度控制 */ \
{ Test_RouteLog,          200U, 0U }, /* 激活路线调试页 */ \
{ LCD_Update,              20U, 0U }, /* LCD非阻塞刷新 */ \
{ OLED_Update,             20U, 0U }, /* OLED非阻塞刷新 */ \
};
```

`Test_RouteLog()`保留函数名用于兼容现有任务表示例，但只激活`ROUTE TEST`页面，不再发送USART1数据；`LCD_Update()`负责LCD约200 ms刷新，`OLED_Update()`负责OLED A/B两页自动切换。因此路线调试数据不会占用E220带宽。

## 二、修改车辆运动控制参数：Algorithm/control_config.h

所有底盘、循迹和动作控制调参宏统一放在 `Algorithm/control_config.h`：

- `CONTROL_CHASSIS_*`：底盘PWM前馈、车轮速度PI、目标斜坡、编码器安全保护、命令租约看门狗和目标/输出限幅；
- `CONTROL_LINE_*`：灰度位置PD、加减速和丢线扫描；
- `CONTROL_MOTION_*`：直行/定角动作的容差、统一速度、越界回正速度、超时和转向比例；所有路线模式和测试入口共用，不再设置路线专用转弯速度。

不要再把参数复制到`APP/chassis.h`、`APP/motion_action.h`、`Algorithm/line_track.h`或`Route`文件中。灰度位置PD只生成上层`linear/turn`目标，底盘统一执行差速分配、PWM前馈和各驱动轮独立PI；外环与内环必须分别调节。

当前通过测试的底盘基线为：

```c
#define CONTROL_CHASSIS_SPEED_LOOP_ENABLE           1U
#define CONTROL_CHASSIS_PWM_MAX_PERMILLE           800
#define CONTROL_CHASSIS_TARGET_MAX_CPS             5000
#define CONTROL_CHASSIS_FEEDFORWARD_FULL_SPEED_CPS 5000
#define CONTROL_CHASSIS_SPEED_KP                    0.08f
#define CONTROL_CHASSIS_SPEED_KI                    0.002f
#define CONTROL_CHASSIS_SPEED_KD                    0.0f
#define CONTROL_CHASSIS_SPEED_INTEGRAL_LIMIT        20000.0f
#define CONTROL_CHASSIS_TARGET_SLEW_STEP_CPS        200
#define CONTROL_CHASSIS_ENCODER_FAULT_ENABLE        1U
#define CONTROL_CHASSIS_FAULT_MIN_TARGET_CPS        800
#define CONTROL_CHASSIS_FAULT_MIN_OUTPUT_PERMILLE   160
#define CONTROL_CHASSIS_FAULT_MAX_FEEDBACK_CPS      200
#define CONTROL_CHASSIS_NO_FEEDBACK_TIMEOUT_MS      500U
#define CONTROL_CHASSIS_DIRECTION_MIN_FEEDBACK_CPS  300
#define CONTROL_CHASSIS_DIRECTION_TIMEOUT_MS        500U
#define CONTROL_CHASSIS_FAULT_CLEAR_MAX_CPS         100
#define CONTROL_CHASSIS_COMMAND_WATCHDOG_ENABLE     1U
#define CONTROL_CHASSIS_COMMAND_TIMEOUT_MS          200U
```

- `CONTROL_CHASSIS_SPEED_LOOP_ENABLE=1U`启用前馈＋PI；改成`0U`可临时退回固定前馈开环，用于标定和排障。
- `CONTROL_CHASSIS_TARGET_MAX_CPS`只限制上层目标；`CONTROL_CHASSIS_FEEDFORWARD_FULL_SPEED_CPS`只标定前馈比例，不要混用。
- 速度环按10 ms周期整定；改变`Chassis_Update`周期后必须重新调节`KI`，不能直接沿用当前值。
- 当前`KD=0`，编码器离散速度通常不需要微分。一次只改一个参数，先稳定车轮内环，再调整循迹PD。
- `CONTROL_CHASSIS_TARGET_SLEW_STEP_CPS`是每次`Chassis_Update()`允许的最大目标变化量；减小会更平滑但响应更慢，停车和急停不经过斜坡。
- 编码器故障保护只在`CONTROL_CHASSIS_SPEED_LOOP_ENABLE=1U`且`CONTROL_CHASSIS_ENCODER_FAULT_ENABLE=1U`时生效。正常使用不要为了绕过故障而关闭保护。
- 无反馈故障同时受目标、PWM、反馈和持续时间四类门槛约束；方向故障要求目标与PWM同向、反馈反向且达到最小反馈速度。调整任一门槛后必须重新进行断线、方向错误、正常低速和起步测试。
- 故障清除门槛由`CONTROL_CHASSIS_FAULT_CLEAR_MAX_CPS`控制。只有底盘已停止且所有启用车轮的原始速度都不超过该值，`Chassis_ClearFault()`才会成功。
- `CONTROL_CHASSIS_COMMAND_WATCHDOG_ENABLE=1U`时，速度模式的当前拥有者必须在`CONTROL_CHASSIS_COMMAND_TIMEOUT_MS`内周期性调用`Chassis_SetSpeed()`刷新命令租约；停止模式不计超时。默认10 ms控制任务配200 ms超时，已经通过普通底盘、Motion和Basic循迹回归测试。
- 调小`CONTROL_CHASSIS_COMMAND_TIMEOUT_MS`会更快发现命令源停止，调大会提高对任务抖动的容忍度。修改后至少验证正常任务长期不误触发、故意停止刷新会锁存`CHASSIS_FAULT_COMMAND_TIMEOUT`、故障期间拒绝重新启动、KEY5停车后可清除。该软件保护依赖`Chassis_Update()`仍在运行，不能替代覆盖整机卡死的硬件独立看门狗。

编码器控制反馈的低通参数位于`Driver/drv_encoder.h`：

```c
#define DRV_ENCODER_SPEED_FILTER_ENABLE       1U
#define DRV_ENCODER_SPEED_FILTER_ALPHA_NUM    1L
#define DRV_ENCODER_SPEED_FILTER_ALPHA_DEN    4L
```

默认`1/4`已经通过当前速度环和循迹测试。改成`1/2`响应更快但噪声更明显，改成`1/6`更平滑但延迟更大。

传感器整体旋转180度后若循迹左右相反，只修改：

```c
#define CONTROL_LINE_DIRECTION_REVERSE 1U
```

正常安装方向使用`0U`。该宏会统一反转循迹误差、`black_mask`和左右分支类型，但不会倒序八路阈值。只改变安装朝向时，不要同时修改Driver中的`DRV_GRAY_MCU_INDEX_REVERSE`或`DRV_GRAY_4051_INDEX_REVERSE`；否则两层反向可能互相抵消。

当前通过测试的丢线恢复参数为：

```c
#define CONTROL_LINE_LOST_CONFIRM_SAMPLES         2U
#define CONTROL_LINE_REACQUIRE_CONFIRM_SAMPLES    3U
#define CONTROL_LINE_SEARCH_TURN_CPS              1000
#define CONTROL_LINE_SEARCH_TURN_STEP_CPS         200
#define CONTROL_LINE_SEARCH_TURN_MAX_CPS          1800
#define CONTROL_LINE_SEARCH_INITIAL_PHASE_MS      300U
#define CONTROL_LINE_SEARCH_PHASE_STEP_MS         200U
#define CONTROL_LINE_SEARCH_PHASE_MAX_MS          900U
#define CONTROL_LINE_SEARCH_TIMEOUT_MS            10000U
```

- 丢线确认和重新捕获参数按`LineTrack_Update()`调用次数计数；当前10 ms周期分别约为20 ms和30 ms。
- 搜索从最后线路方向开始，随后逐阶段反向；转向量由1000 cps每阶段增加200 cps，最高1800 cps。
- 扫描时间由300 ms每阶段增加200 ms，最高900 ms；从首次丢线累计10秒后安全停车。
- 调整搜索参数后必须分别验证左侧丢线、右侧丢线、重新捕获和超时停车，不能只验证一个方向。

各`CONTROL_*`宏的逐项用途、单位、调高/调低影响和推荐调试顺序，统一查阅`Doc/参数和引脚说明.md`第一、二节。2026-07-20已完成默认2WD车轮速度内环、目标斜坡、编码器故障保护、命令租约看门狗、分阶段丢线恢复和Basic循迹回归测试；进入后续动作库和新赛道调试时先冻结当前内环及安全门槛参数，避免同时修改内环和外层参数而无法判断问题来源。

### （一）修改五按键底盘速度测试目标：Test/test.c

手动切回五按键底盘速度测试时，使用以下四个测试专用宏：

```c
#define TEST_CHASSIS_INITIAL_LINEAR_CPS  1600
#define TEST_CHASSIS_LINEAR_STEP_CPS      200
#define TEST_CHASSIS_LINEAR_MAX_CPS      4800
#define TEST_CHASSIS_TURN_CPS            1600
```

- `TEST_CHASSIS_INITIAL_LINEAR_CPS`：按 KEY1 时的前进速度，同时重置当前加速档位。
- `TEST_CHASSIS_LINEAR_STEP_CPS`：每次按 KEY2 增加的速度。
- `TEST_CHASSIS_LINEAR_MAX_CPS`：KEY2 可增加到的最大前进速度，不应超过 `CONTROL_CHASSIS_TARGET_MAX_CPS`。
- `TEST_CHASSIS_TURN_CPS`：KEY3/KEY4 原地转向时的转向速度绝对值。

这些宏只影响 `Test_ChassisCmd_Update()` 调试入口，不改变循迹、Route 或 Motion 的正式控制参数。

## 三、切换双路、四路驱动的宏：BSP/vehicle_config.h

```c
#define VEHICLE_DRIVE_MODE_2WD             2U
#define VEHICLE_DRIVE_MODE_4WD             4U
#ifndef VEHICLE_DRIVE_MODE
#define VEHICLE_DRIVE_MODE                 VEHICLE_DRIVE_MODE_2WD
```

说明：2WD 时 SPI1 可用于 LCD；4WD 时 PA6/PA7 被后编码器占用，当前代码会让 LCD 改用 SPI2，与 ICM-20948 共用总线。I2C/SPI外设初始化统一由`BSP_InitAll()`负责，Driver只做设备级初始化，不应再次调用`BSP_I2C_Init()`或`BSP_SPI_Init()`。

建议：4WD 下在联合验证完成前，将 APP/lcd_ui.h 中的 LCD_UI_ENABLE 设为 0U，暂不使用 LCD。

```c
#define LINE_DETECT_DEFAULT_THRESHOLD_0 1582
#define LINE_DETECT_DEFAULT_THRESHOLD_1 1662
#define LINE_DETECT_DEFAULT_THRESHOLD_2 2730
#define LINE_DETECT_DEFAULT_THRESHOLD_3 2385
```

## 八、修改红绿状态灯有效电平：BSP/bsp_gpio.h

```c
#define BSP_GPIO_STATUS_RED_ACTIVE_LEVEL     1U
#define BSP_GPIO_STATUS_GREEN_ACTIVE_LEVEL   1U
```

当前PG5红灯、PG6绿灯均按高电平点亮完成实物测试，因此保持`1U`。只有更换为低电平有效的灯板后才改为`0U`；对应GPIO上电初始电平会自动取反，继续保持上电熄灭。正式业务只调用`Driver/drv_status_light.h`中的控制接口，不在APP或Route中直接写GPIO电平。

## 九、修改蜂鸣器有效电平：BSP/bsp_gpio.h

```c
#define BSP_GPIO_BUZZER_ACTIVE_LEVEL  0U
```

当前PG7配置为低电平鸣响：`0U`表示低电平有效，`1U`表示高电平有效。对应GPIO上电初始电平会自动取反，始终保持上电关闭。仓库尚无实板蜂鸣器验收记录，实际模块有效电平和响声待确认；只允许修改这个BSP宏，不要在`Driver`、`APP`或`Test`中额外反转电平。

专项测试入口为`Test_Buzzer_Update()`：KEY1持续鸣响、KEY2停止、KEY3每500 ms翻转，任务表必须先注册`Key_Update()`。完整任务表示例见《测试任务注册函数使用方法》。

## 十、修改送药状态机和Medicine路线参数

初始数字、称重门槛和视觉确认参数位于`APP/task_fsm.h`：

```c
#define TASK_FSM_TARGET_CONFIRM_FRAMES          3U
#define TASK_FSM_TARGET_MIN_CONFIDENCE         70U
#define TASK_FSM_VISION_CONFIRM_FRAMES          2U
#define TASK_FSM_VISION_ABSENCE_CONFIRM_FRAMES  2U
#define TASK_FSM_LOAD_ON_THRESHOLD_G         120.0f
#define TASK_FSM_LOAD_OFF_THRESHOLD_G         50.0f
#define TASK_FSM_WEIGHT_CONFIRM_MS           500U
#define TASK_FSM_STARTUP_TARE_DELAY_MS        500U
```

`TASK_FSM_TARGET_MIN_CONFIDENCE`只用于行驶中的路口视觉决策；初始处方数字由K210稳定输出后，STM32只要求画面中恰好一个1～8数字并连续确认3个新快照。调整称重门槛时必须保持装药上门槛大于卸药下门槛，并重新实测约200 g药品的装载和取走过程。正式任务启动去皮前托盘必须空载。

路线参数位于`Route/route_profile_medicine.h`：

```c
#define MEDICINE_ROUTE_EVENT_CONFIRM_SAMPLES       3U
#define MEDICINE_ROUTE_END_CONFIRM_SAMPLES         2U
#define MEDICINE_ROUTE_SINGLE_CONFIRM_SAMPLES      3U
#define MEDICINE_ROUTE_DOOR_MIN_SEGMENTS            2U
#define MEDICINE_ROUTE_VISION_APPROACH_MAX_CPS    1600
#define MEDICINE_ROUTE_END_MIN_TRAVEL_MM           250L
#define MEDICINE_ROUTE_RETURN_SPEED_BOOST_CPS       500
#define MEDICINE_ROUTE_RETURN_MAX_SPEED_CPS        3000
#define MEDICINE_ROUTE_RIGHT_ANGLE_DEG              55
#define MEDICINE_ROUTE_EVENT_IGNORE_MS            400U
```

- 十字路口仍转过头时，小步降低`MEDICINE_ROUTE_RIGHT_ANGLE_DEG`；该值只改变Medicine左右路口动作，不改变180°病房掉头。
- 行驶中来不及识别数字时降低`MEDICINE_ROUTE_VISION_APPROACH_MAX_CPS`，不要用路口停车后再识别代替路口前识别。
- 返程巡线速度只改`MEDICINE_ROUTE_RETURN_SPEED_BOOST_CPS`和`MEDICINE_ROUTE_RETURN_MAX_SPEED_CPS`。加速仅作用于正常单线，Motion转弯仍由`CONTROL_MOTION_TURN_*`统一控制。
- 病房或药房提前停车时先检查门标灰度位图和路口计数，再考虑增大`MEDICINE_ROUTE_END_MIN_TRAVEL_MM`；不要把普通丢线改成到达条件。
- 门标偶尔漏判时先核对灰度阈值、安装高度和黑白虚线是否形成至少2个分离黑段，再调整确认样本数。

修改这些参数后必须重新验证1/2号近端、3～8号中部和远端路线，以及返程经过近端数字区域时不会提前亮绿灯。

## 十一、选择或新增总任务状态机和赛道

两类选择相互独立，但都是编译期选择，修改后必须重新全量编译和烧录，不能在车辆运行中热切换。

### （一）选择总任务状态机

在`APP/task_profile_config.h`修改：

```c
#define TASK_PROFILE_NONE                         0U
#define TASK_PROFILE_MEDICINE                     1U
#define TASK_PROFILE_SELECT                       TASK_PROFILE_MEDICINE
```

- `TASK_PROFILE_MEDICINE`：当前送药比赛总状态机。
- `TASK_PROFILE_NONE`：不运行总任务状态机，适合Basic循迹或底层分项测试。
- 正式任务表固定注册`TaskProfile_Update()`，不要再直接注册具体的`TaskFSM_Update()`。
- 正式任务表的`AppDiagnostics_TaskFSMLogUpdate`当前只认识Medicine状态机；切换到其他状态机后应移除，并为新状态机提供自己的正式诊断函数。`Test_TaskFSM_Log`仅在启用`Test`目录后用于专项测试。

新增状态机时按以下步骤接入：

1. 在`APP/`新增自己的`.c/.h`，至少提供非阻塞的`XxxTask_Init()`、`XxxTask_Reset()`和`XxxTask_Update()`。
2. 在`task_profile_config.h`为它增加不重复的`TASK_PROFILE_XXX`编号。
3. 在`task_profile_select.c`增加对应的`#elif`、头文件和`TaskProfile_Init/Reset/Update`三处转发。
4. 若该状态机只支持某个赛道，在选择分支中用`#if`和`#error`声明兼容要求，避免错误组合通过编译。
5. 把新`.c/.h`加入`DroneProject.uvprojx`，并把`.c`加入`Makefile`源文件列表。
6. 将`TASK_PROFILE_SELECT`改为新编号，完整重编译；任务表仍调用`TaskProfile_Update()`。

### （二）选择或新增赛道

在`Route/route_config.h`修改：

```c
#define ROUTE_PROFILE_BASIC                         0U
#define ROUTE_PROFILE_MEDICINE                      1U
#define ROUTE_PROFILE_SELECT                        ROUTE_PROFILE_MEDICINE
```

新增赛道时：

1. 新建`Route/route_profile_xxx.c/.h`，完整实现`Init`、`Reset`、`ConfigureMission`、`SubmitVisualDecision`、`Update`和`GetInfo`六类接口，参数和返回类型与`route_profile_select.h`一致。
2. 在`route_config.h`增加不重复的`ROUTE_PROFILE_XXX`编号。
3. 在`route_profile_select.c`增加头文件选择，并在全部`RouteProfile_*`统一接口中增加转发分支。
4. 把新文件加入Keil工程和`Makefile`。
5. 修改`ROUTE_PROFILE_SELECT`后全量编译；遗漏任一适配分支或使用未知编号时应由编译错误暴露，不能用默认路线静默兜底。

当前兼容组合为：Medicine状态机＋Medicine赛道用于正式送药；`TASK_PROFILE_NONE`可配Basic或Medicine进行独立路线/底层测试；Medicine状态机＋Basic赛道会被编译期拒绝。新增方案必须自己定义并验证兼容关系。
