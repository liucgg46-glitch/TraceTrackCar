# 注意事项

> 本文按当前项目源码校正。当前 `Doc` 目录未发现对应的 Word 原文件；若后续恢复 Word 文件，必须同时检查本文和 `说明文档.md`。

## 一、OLED 和 LCD 注意事项

### （一）LCD

- 开机初始页：修改 `APP/lcd_ui.c` 中的 `LcdUi_DrawBaseStep()`。
- 运行页底图/边框：修改 `LcdUi_DrawRunBaseStep()`。
- LCD运行时实时内容：统一修改`LcdUi_ShowDashboard()`。普通任务显示正常仪表盘；`Test_ChassisCmd_Update()`切换到底盘速度测试页；`Test_RouteLog()`切换到路线测试页；`LineCalibration_Update()`切换到灰度校准页。
- OLED专用页由同一业务任务激活：`Test_RouteLog()`调用`OledUi_RouteTestBegin()`，`LineCalibration_Update()`调用OLED标定页面接口。只有同时注册`OLED_Update()`时OLED才持续显示；路线数据因高度限制分A/B两页自动切换。
- 临时状态提示：使用 `LcdUi_ShowStatus()`。
- `LcdUi_Update()` 只负责刷新调度和页面切换，一般不在这里添加显示内容。
- LCD是SPI屏，没有整屏RAM缓冲，所以启动页、正常仪表盘、底盘速度测试页、路线测试页和校准页面都采用分步绘制，避免长时间阻塞。专用测试页需要以20 ms周期注册`LCD_Update`，约每200 ms完成一次10行数据刷新。

### （二）OLED

- 开机初始页：修改 `APP/oled_ui.c` 中的 `OledUi_DrawBase()`。
- 运行页底图/边框：修改 `OledUi_DrawRunBase()`。
- 运行时实时内容：统一修改 `OledUi_ShowDashboard()`。
- 临时状态提示：使用 `OledUi_ShowStatus()`。
- `OledUi_Update()` 只负责刷新周期和页面切换，一般不在这里添加显示内容。

### （三）简单记忆

- 改开机内容：LCD 使用 `LcdUi_DrawBaseStep()`；OLED 使用 `OledUi_DrawBase()`。
- 改运行固定内容：LCD 使用 `LcdUi_DrawRunBase()`；OLED 使用 `OledUi_DrawRunBase()`。
- 改动态仪表：LCD 使用 `LcdUi_ShowDashboard()`；OLED 使用 `OledUi_ShowDashboard()`。
- 改状态提示：LCD 使用 `LcdUi_ShowStatus()`；OLED 使用 `OledUi_ShowStatus()`。
- 定时调用：LCD 使用 `LCD_Update()`；OLED 使用 `OLED_Update()`；更新函数只负责刷新调度，不直接编写页面内容。

## 二、增加普通 GPIO 时的注意事项

在 BSP/bsp_gpio.h 中统一管理所有普通 GPIO。新增通道时，应同时核对引脚复用冲突，并通过业务别名使用，避免在业务代码中直接散落 CH 编号。

PG5和PG6已经分别分配给红色、绿色状态灯，当前实物按高电平有效测试通过。业务代码必须通过`Driver/drv_status_light.*`控制，不直接操作`BSP_GPIO_CH21`、`BSP_GPIO_CH22`或端口寄存器；驱动会保证灭、红、绿三种状态互斥。

题目规定任一指示灯点亮时小车必须停止。送药状态机应先调用统一停车入口并确认车辆进入停止状态，再点亮红灯或绿灯；不得用“点灯”代替停车命令。普通小功率LED必须串联合适的限流电阻，若使用灯条、大功率灯或超过GPIO驱动能力的模块，应增加三极管/MOS管驱动，不能由STM32引脚直接供电。

当前 `BSP/bsp_key.h` 已把 PA15 暂按内部上拉、低电平按下配置为 `BSP_KEY5`；仓库没有开发板原理图，实际有效电平待确认。PA15 也是 JTDI 复用脚，因此该配置不保留完整 JTAG；项目仍保留 PA13/PA14 的两线 SWD，烧录和调试应选择 SWD。PA15 虽也可复用 TIM2_CH1/ETR，但当前 TIM2 编码器使用 PA0/PA1，KEY5 不会占用定时器本体。

当前默认动作库测试把 KEY5 作为软件停止键，调用`Motion_Stop()`取消动作并停车。由于 KEY5 的板级电路和实际有效电平仍待确认，首次测试必须悬空车轮，并预留可直接切断电机功率电源的硬件手段；在实板确认 KEY5 能稳定触发前，不得把它当作唯一急停措施。

当前动作库测试任务表没有注册`LCD_Update()`，因此LCD不显示动作测试数据；需要闭环测试页时必须手动切回`Test_ChassisCmd_Update()`与`LCD_Update()`对应的任务表。

## 三、E220 AUX 与 USART1 注意事项

- 当前`VEHICLE_UART1_LINK_MODE`选择`VEHICLE_UART1_LINK_DIRECT`，USART1用于普通直连串口日志，PE6的E220 AUX通道不启用；使用E220前必须显式切换为`VEHICLE_UART1_LINK_E220`并重新编译。
- AUX 可以不接，但既然本项目选择接入，代码会在 AUX 为低电平时将新的完整帧保存到 E220 软件队列，等 AUX 变高后重试。不接 AUX 时若仍选择 E220 模式，PE6 会悬空，读值不可靠，因此必须改回普通模式或可靠接好 AUX。
- AUX 是 E220 的输出，只接 STM32 普通数字输入 PE6，使用 `GPIO_Mode_IN + GPIO_PuPd_NOPULL`；不需要专用外设或外部中断。
- AUX 绝不能接 5V、3.3V 或其他外部“高电平”电源，也不能由 MCU 配成推挽输出。给模块供电的是独立的 `VCC` 引脚；AUX 与 RXD/TXD 都是 3.3V IO。
- 严禁把 AUX 接到会主动输出低电平的 MCU 引脚配置，也不要外接下拉。手册说明模块上电早期若 AUX 被持续拉低，可能强制进入升级模式并无法正常收发。
- AUX 高电平主要表示模块串口缓存可继续接收，并不在所有固件/`AT+UAUX` 配置下都等价于“最后一包已经完成空中发送”。低空速或连续大数据仍需由上层限速。
- 115200 是 STM32↔E220 的本地 UART 波特率，不是无线空中速率。分包、空中速率、纠错、信号质量和接收端显示都会让无线输出明显慢于 USB-TTL 直连，这是正常现象。

## 四、E220 发送速度与软件队列

- 软件队列按完整帧 FIFO 保存，默认 16 帧、每帧最大 512 字节；成功保存时 `BSP_UART_WriteFrame()` 返回 `BSP_OK`。队列满或帧超长仍无法保存，应用可通过 `Drv_E220_GetTxStats()` 查看统计。
- 队列只能吸收短时拥塞，不能提升物理吞吐。如果其他串口任务导致`queue_full_frames`增长，应降低其日志频率或调整模块空中参数；`Test_RouteLog`已改为LCD/OLED页面激活任务，不再占用USART1或E220队列。
- AUX 变低的正常原因包括：模块刚上电或复位、工作模式切换、收到 STM32 的串口数据并进行断帧/缓存、缓存超过分包长度后循环空中发送，以及接收无线数据后准备从 TXD 输出。若启用了 `AT+UAUX=1` 或使用较旧固件，AUX 还会在整个无线发射期间保持低电平。
- 提速优先检查两端 `AT+RATE`，两端必须一致；可从默认 2.4 kbps 逐步提高到 4.8/9.6/19.2/38.4/62.5 kbps，但速率越高，灵敏度和可靠距离越低。较新固件可用 `AT+UAUX=0` 让 AUX 不跟踪整个空中发送过程；这只允许更快地向 400 字节模块缓存送数据，不会提高空口本身速率。
- `AT+PACKET` 建议先保持 200 字节或按完整业务帧选择 128 字节；32/64 字节会把一行长日志拆成更多无线包，协议开销可能反而增大。若启用 LBT，发射前监听也会引入延迟；WOR 模式还会引入 500～4000 ms 周期延迟，因此实时日志应使用 M0=M1=0 的传输模式。
- 路线调试信息显示在LCD/OLED的`ROUTE TEST`页面；必须注册`Test_RouteLog`，并为需要显示的屏幕注册`LCD_Update`或`OLED_Update`。原始/滤波误差、丢线时间和扫描阶段不再通过USART1或E220发送。

## 五、循迹控制参数和丢线恢复

- 车辆运动调参只修改 `Algorithm/control_config.h`。不要在 Route、`chassis.h`、`motion_action.h` 或 `line_track.h` 中重复定义增益。
- 灰度位置PD只生成`linear/turn`目标；底盘统一完成差速分配、PWM前馈和各驱动轮独立PI速度闭环。循迹、Motion和Route不得绕过`Chassis_SetSpeed()`直接写电机。
- `Encoder_Update`必须以10 ms周期注册在`Chassis_Update`之前。速度PI使用`Drv_Encoder_GetWheelSpeedCps()`的滤波反馈；原始速度只用于日志和排障。
- 所有启用驱动轮的编码器反馈都必须有效。闭环开启且保护启用时，达到监控目标/PWM门槛后，反馈连续500 ms过低会锁存无反馈故障，反馈连续500 ms反向会锁存方向故障；底盘随即停车并释放控制权。软件无法区分编码器断线、接头松动与机械堵转，触发后仍必须检查硬件，不得只清除故障继续运行。
- 故障不会被`Chassis_EmergencyStop()`自动清除。修复原因后，必须等待底盘处于停止状态且所有启用车轮原始速度绝对值不超过100 cps，再显式调用`Chassis_ClearFault()`；专项测试的KEY5会先急停再尝试清除，车轮未停稳时需等待后再按一次。
- 当前默认2WD速度环、200 cps/10 ms目标斜坡、编码器故障保护和200 ms命令租约看门狗已在1600 cps、阶跃加速、专项超时、Motion与Basic循迹中通过测试。更换电机、轮胎、供电、负载或10 ms任务周期后必须重新验证，且一次只调内环、安全门槛或外环中的一类参数。
- 当前MCU-I2C灰度模块、逐路阈值和循迹参数已经沿赛题红色实线完成实车测试。算法中的`BLACK`命名表示相对白底更深的线路响应；更换红色胶带材质、光照、安装高度或底板后仍需重新检查八路读数和阈值。
- 普通循迹会限制`|turn| <= linear`，避免大偏差时内侧轮反转；独立边缘救线模式已经取消，丢线扫描仍允许左右轮反向。
- 丢线先连续确认 2 帧，再沿最后一次线路方向扫描 300ms；之后反向，并逐阶段增加扫描时间和转速。重新看到线必须连续确认 3 帧才退出搜索，避免传感器噪声造成小幅来回抖动。
- 连续搜索超过`CONTROL_LINE_SEARCH_TIMEOUT_MS`会输出无效，循迹APP通过异常中止路径安全停车并暂时保留`MODE:SAFE`诊断状态；下一次KEY1开始或KEY4人工停止会通过`RouteManager_Reset()`清除旧误差、旧速度、搜索状态和旧Motion动作。
- Basic模式把所有未预先声明的丢线都视为意外丢线。后续赛道若题目要求主动离线行驶，必须由对应Route状态在丢线前切换到`ROUTE_CONTROL_MOTION`执行定距/定角动作，动作期间不要调用`LineTrack_Compute()`；禁止全局关闭丢线保护。
- 底盘命令必须携带控制权拥有者：循迹使用`CHASSIS_OWNER_LINE_FOLLOW`，动作库使用`CHASSIS_OWNER_MOTION`，底盘专项测试使用`CHASSIS_OWNER_TEST`。普通模块不得绕过`Chassis_AcquireControl()`直接覆盖其他模块的命令；停止、完成或错误退出后必须释放控制权。
- 底盘速度命令是有时限的租约，不是一次设置后永久有效。速度模式拥有者必须在默认200 ms超时前周期性调用`Chassis_SetSpeed()`；当前10 ms周期的循迹、Motion和普通底盘测试都会持续刷新。命令源停止刷新而`Chassis_Update()`仍运行时，会锁存`CHASSIS_FAULT_COMMAND_TIMEOUT`（`fault=3 mask=00`）、立即停车并释放控制权，修复原因后按普通故障流程显式清除。
- 命令租约看门狗只能处理“底盘任务仍运行、上层命令源不再刷新”，不能处理整个调度器或MCU停止执行。需要覆盖整机卡死、主循环阻塞或时钟异常时，应另外启用并正确喂养硬件独立看门狗；不要把软件租约描述为整机看门狗。
- Route层只能产生`Route_ControlMode_t`、`Route_ActionRequest_t`等控制意图，不得直接包含或调用APP、Motion、底盘和具体传感器模块。赛道切换统一在`route_config.h`和`route_profile_select.*`接入。
- E220 透明传输模式下 M0、M1 必须可靠接低电平且不可悬空。PA9 接 E220 RXD，PA10 接 E220 TXD。STM32 只需与本地 E220 共地，电脑端 E220 只需与本地 USB-TTL 共地；两台远端 E220 之间不需要连接 GND。
- 普通模式和 E220 模式共用 PA9/PA10，只能选择一种外部接线。不要把 USB-TTL TX 与 E220 TXD 同时并接到 PA10，否则两个推挽输出可能发生电气冲突。
- PE6 在当前源码资源表中没有发现冲突，但实际开发板是否已引出以及是否连接板载器件仍为“待确认”。
- HX711已固化实测`695.93 counts/g`。上电时称重台必须空载：HX711专项测试等待驱动约3.2秒稳定自动去皮；正式送药状态机若克重仍无效，会在`WAIT_TARGET`空载阶段约500 ms后调用`Sensor_PressureTare()`建立零点。两种模式都禁止带载上电或在去皮前放药，否则负载会被当作零点。

## 六、K210数字识别通信注意事项

- 当前通过测试的单向接线是K210 IO6/UART1_TX→STM32 PA3/USART2_RX，两板必须共地；历史旧资料中的IO8 TX结论不适用于当前仓库和SD卡运行版本。
- K210实际运行的Python启动入口、识别程序和模型已经同步到仓库`K210/`目录。修改模型、`LABELS`、`ANCHORS`、串口引脚、波特率或协议时必须同步更新仓库与SD卡，不能只改其中一份，也不能根据旧示例猜测。
- K210需要稳定且电流充足、符合模块规格的电源，不建议直接使用STM32开发板的3.3V引脚供电。分别供电时仍必须共地，接线和拔线前先断电。
- 使用USB-TTL查看`Test_K210_CommUpdate()`日志时，USART1选择`VEHICLE_UART1_LINK_DIRECT`。不要把USB-TTL TX与E220 TXD同时并接到PA10；两者都是推挽输出，可能产生电气冲突。
- `K210_Comm_Update()`负责协议解析，正式程序必须周期调用；`Test_K210_CommUpdate()`只负责观察日志，不得在其中加入停车、转向或电机控制。
- 初始处方通过`K210_Comm_ReadDigits()`只读取K210已稳定输出的数字值，要求画面中恰好一个1～8数字并连续确认3个新快照；行驶中的路口选路才读取完整快照并检查在线状态、快照状态、目标置信度、横坐标和结果时效。通信离线或结果超时后不得继续使用旧数字控制车辆。
- `K210_MAX_DIGITS=8`只表示STM32缓存容量，不表示画面必须识别固定数量；不得为了业务预期补足数字或静默裁剪多余结果。
- 正式业务已经由`TaskFSM_Update()`和Medicine Route接入K210快照；1/2号按固定近端路线，3～8号按随机中部/远端位置在行驶中选路。病房和药房到达只认灰度阵列的黑白虚线门标，不认“数字消失”或普通丢线；返程还必须先通过对应层级的0/1/2个主路路口并满足250 mm门控。整车已完成基础比赛流程的主要实车联调，通信解析、任务决策、路线状态和底盘控制必须继续保持分层。
- 返程加速只作用于`LINE_TYPE_SINGLE`正常单线段：当前在线路算法输出上增加500 cps并限制到3000 cps。十字、分支、丢线和所有Motion定角动作保持原参数；不要把返程巡线速度和180°掉头速度混为同一项。
