# 测试任务注册函数使用方法

> 本文按当前项目源码校正。当前 `Doc` 目录未发现对应的 Word 原文件，因此本次只能同步 Markdown；若后续恢复 Word 文件，必须同时检查本文和 `说明文档.md`。

## 测试代码启用与恢复

专项测试代码已从`Driver`移到独立的`Test`目录，正式固件默认不编译任何`Test_*`任务函数。执行本文中的分项测试前必须完成两步：

1. 把`Test/test_config.h`中的`PROJECT_TEST_TASKS_ENABLE`改为`1U`。
2. 在`APP/app_task_config.h`中临时添加`#include "test.h"`，再替换为本文对应的测试任务表。

测试结束后必须把`PROJECT_TEST_TASKS_ENABLE`恢复为`0U`，移除临时的`#include "test.h"`并恢复正式任务表。正式固件的运行指示灯和状态机日志分别由`AppDiagnostics_HeartbeatUpdate()`、`AppDiagnostics_TaskFSMLogUpdate()`提供，不依赖`Test/test.c`。`AppTask_BSP_Background()`在正式和测试任务表中都必须保留。

## 姿态算法主机单元测试

姿态算法主机测试不使用STM32任务表，也不需要修改`PROJECT_TEST_TASKS_ENABLE`。在项目根目录执行：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Test\host\run_attitude_tests.ps1
```

脚本使用Visual Studio C++ x64工具链直接编译真实的`Algorithm/attitude_estimator.c`，通过`Test/host/stubs/bsp_common.h`替代最小BSP接口，构建产物写入系统临时目录。当前稳定用例覆盖静止输入、Z轴匀速旋转、重复时间戳、无效输入与恢复、`motor_active`磁力计屏蔽与恢复，共5项；2026-07-22运行结果为5项全部通过。详细说明见`Test/host/README.md`。

## 五按键动作库测试

需要单独测试动作库时，使用以下稳定任务组合：

```c
Task_t task_list[] = { \
{ Test_GPIO_Toggle,        10U, 0U }, \
{ AppTask_BSP_Background,   1U, 0U }, \
{ Key_Update,              10U, 0U }, \
{ Sensor_Update,            1U, 0U }, \
{ Encoder_Update,          10U, 0U }, \
{ Test_MotionCmd_Update,   10U, 0U }, \
{ Motion_Update,           10U, 0U }, \
{ Chassis_Update,          10U, 0U }, \
{ Test_MotionCmd_Log,     200U, 0U }, \
};
```

`Key_Update()`必须排在`Test_MotionCmd_Update()`之前，以生成消抖后的按下沿事件；`Sensor_Update()`和`Encoder_Update()`必须先于动作更新。KEY1/KEY2的定角动作会检查IMU是否完成初始化和静止标定，未准备好时拒绝启动。本示例不注册`LCD_Update()`，因此动作测试不在LCD上显示，只通过USART1输出命令结果和周期日志。`Test_GPIO_Toggle`是常驻运行指示灯，不能省略。

灰度按键校准和Basic路线循迹使用本文后面的独立稳定示例；`LineCalibration_Update()`位于正式的`APP/line_calibration.c`。

## 五按键专项测试（需要手动切换任务表）

要单独检查 KEY1～KEY5 时，将任务表切换为：

```c
Task_t task_list[] = { \
{ Test_GPIO_Toggle,       10U, 0U }, \
{ AppTask_BSP_Background,  1U, 0U }, \
{ Key_Update,             10U, 0U }, \
{ Test_Key_Update,        10U, 0U }, \
};
```

`Key_Update()` 负责调用 `BSP_Key_UpdateAll()` 完成扫描和 20 ms 消抖，`Test_Key_Update()` 只读取并打印事件。两者都使用 10 ms 周期，并且 `Key_Update()` 必须排在前面。按键专项测试不需要注册 `Sensor_Update()`。USART1 使用 115200、8-N-1；普通直连模式下接 USB-TTL，E220 模式下日志从无线链路发出。

上电后先发送：

```text
KEY TEST READY: KEY1=PE4 KEY2=PE3 KEY3=PE2 KEY4=PE1 KEY5=PA15
```

每个按键稳定按下和松开各发送一行：

| 操作 | USART1 输出 |
| --- | --- |
| 按下/松开 KEY1（PE4） | `KEY1 PRESSED (PE4)` / `KEY1 RELEASED (PE4)` |
| 按下/松开 KEY2（PE3） | `KEY2 PRESSED (PE3)` / `KEY2 RELEASED (PE3)` |
| 按下/松开 KEY3（PE2） | `KEY3 PRESSED (PE2)` / `KEY3 RELEASED (PE2)` |
| 按下/松开 KEY4（PE1） | `KEY4 PRESSED (PE1)` / `KEY4 RELEASED (PE1)` |
| 按下/松开 KEY5（PA15） | `KEY5 PRESSED (PA15)` / `KEY5 RELEASED (PA15)` |

PA15 同时是 JTDI 复用脚。当前配置把它改为普通按键输入，因此完整 JTAG 不再可用；PA13/PA14 两线 SWD 下载和调试不受影响。仓库没有开发板原理图，KEY5 暂按与 KEY1～KEY4 相同的内部上拉、低电平按下方式配置，实际有效电平待实板确认。

## 二、底盘速度闭环测试

```c
Task_t task_list[] = { \
{ Test_GPIO_Toggle,        10U, 0U }, /* 运行指示灯 */ \
{ AppTask_BSP_Background,   1U, 0U }, /* BSP和Driver后台维护 */ \
{ Key_Update,              10U, 0U }, /* 按键扫描 */ \
{ Encoder_Update,          10U, 0U }, /* 编码器测速，必须先于底盘 */ \
{ Test_ChassisCmd_Update,  10U, 0U }, /* 五按键速度命令 */ \
{ Chassis_Update,          10U, 0U }, /* 前馈＋车轮速度PI */ \
{ LCD_Update,              20U, 0U }, /* 可选的LCD非阻塞刷新 */ \
{ Test_ChassisCmd_Log,    200U, 0U }, /* 速度闭环串口日志 */ \
};
```

KEY1（PE4）：线速度重置为 1600 cps 并前进

KEY2（PE3）：KEY1 启动后，线速度增加 200 cps 并继续前进，最大 4800 cps；达到上限后继续按仍保持 4800 cps

KEY3（PE2）：转向速度设为 +1600 cps，原地左转

KEY4（PE1）：转向速度设为 -1600 cps，原地右转

KEY5（PA15）：先调用`Chassis_EmergencyStop()`立即停车并释放底盘控制权，再调用`Chassis_ClearFault()`尝试清除锁存故障

每个按键只处理消抖后的按下沿，按住不会连续加速。速度命令有效期间，`Test_ChassisCmd_Update()`会每10 ms重新调用`Chassis_SetSpeed()`刷新命令租约。上电后或KEY5停止后，KEY2不会单独启动车轮，必须重新按KEY1；KEY1会把加速档位置为1600 cps。若故障发生后车轮仍在转，第一次按KEY5会输出`WAIT WHEELS THEN CLEAR AGAIN`，待所有启用车轮原始速度绝对值不超过100 cps后再按一次。串口每200 ms输出故障、命令年龄、命令目标、斜坡后目标、原始/滤波速度、前馈、PI修正和最终PWM，按键动作也会立即输出一行确认日志。

### 串口日志字段

周期日志格式为：

```text
CHS loop=1 fault=0 mask=00 age=0 owner=3 mode=1 cmd=1600/1600 tgt=1600/1600 raw=1600/1600/0/0 fb=1603/1603/0/0 ff=256/256/0/0 pi=-6/-26/0/0 out=250/230/0/0
```

| 字段 | 含义 |
| --- | --- |
| `loop=0/1` | `1`为前馈＋PI闭环，`0`为固定前馈开环回退 |
| `fault` | `0`无故障，`1`编码器无反馈，`2`编码器反馈方向错误，`3`速度命令租约超时；故障触发后保持锁存 |
| `mask` | 故障车轮位掩码：`01=FL`、`02=FR`、`04=RL`、`08=RR`，多轮故障按位组合 |
| `age` | 最近一次有效`Chassis_SetSpeed()`距当前的时间，单位ms；正常10 ms任务通常约为0～10，命令超时故障不对应车轮，因此`fault=3`时`mask=00` |
| `owner` | 当前底盘控制权拥有者；专项测试使用`CHASSIS_OWNER_TEST` |
| `mode=0/1` | `0`为`CHASSIS_MODE_STOP`，`1`为`CHASSIS_MODE_SPEED` |
| `cmd=L/R` | 左右侧命令目标，单位cps；由`left=linear-turn`、`right=linear+turn`得到 |
| `tgt=L/R` | 经过目标斜坡后真正送入前馈、PI和故障监控的左右侧目标；默认每10 ms最多向`cmd`变化200 cps |
| `raw=FL/FR/RL/RR` | 四轮编码器原始速度；用于检查量化抖动、断线和方向 |
| `fb=FL/FR/RL/RR` | 提供给速度PI的滤波速度；当前2WD下RL/RR为0 |
| `ff=FL/FR/RL/RR` | 按目标速度计算的基础PWM前馈，单位千分比 |
| `pi=FL/FR/RL/RR` | 各驱动轮的PI修正量；反馈为0时会明显增大，不能把这种状态判为测试通过 |
| `out=FL/FR/RL/RR` | `ff+pi`经过最终限幅后的电机PWM千分比；绝对值不超过800，负值表示反转 |

验收时必须同时确认所有启用驱动轮的`raw`和`fb`都非零且符号与`cmd/tgt/out`一致。正常加减速时`cmd`可以立即变化，`tgt`应以每10 ms最多200 cps平滑跟随；KEY5停车不经过斜坡，应立即归零。

### 编码器安全保护验收

该保护只在`CONTROL_CHASSIS_SPEED_LOOP_ENABLE=1U`且`CONTROL_CHASSIS_ENCODER_FAULT_ENABLE=1U`时生效。已经完成测试并确认以下行为：

1. 正常双轮反馈下持续运行，`fault=0 mask=00`，不会误触发。
2. 让某一启用轮在目标绝对值至少800 cps、输出绝对值至少160‰时持续无有效反馈，约500 ms后应出现`fault=1`，`mask`标出对应车轮，`owner=0 mode=0`且全部输出归零。
3. 让某一启用轮反馈绝对值至少300 cps且方向持续与目标、输出相反，约500 ms后应出现`fault=2`并停车锁存。
4. 故障锁存后按KEY1～KEY4应输出`CONTROL BUSY OR FAULT`，不得重新启动。
5. 修复接线或方向后按KEY5。若车轮未停稳先等待，再按一次；成功时输出`STOPPED / FAULT CLEARED`，日志恢复`fault=0 mask=00`。随后必须重新按KEY1启动。

无反馈故障可以由编码器断线、接头松动或机械堵转触发，软件不能自动区分原因。故障测试应悬空车轮、从低速开始并确保可立即断电，不能只反复清除故障而不修复原因。

### 底盘命令租约看门狗专项测试

该测试故意只发送一次速度命令，用于验证上层任务停止刷新时能够自动停车。它必须与`Test_ChassisCmd_Update()`二选一注册，不能同时运行：

```c
Task_t task_list[] = { \
{ Test_GPIO_Toggle,             10U, 0U }, /* 运行指示灯 */ \
{ AppTask_BSP_Background,        1U, 0U }, /* BSP和Driver后台维护 */ \
{ Key_Update,                   10U, 0U }, /* 按键扫描 */ \
{ Encoder_Update,               10U, 0U }, /* 编码器测速 */ \
{ Test_ChassisWatchdog_Update,  10U, 0U }, /* 故意只发送一次命令 */ \
{ Chassis_Update,               10U, 0U }, /* 底盘控制与租约检查 */ \
{ LCD_Update,                   20U, 0U }, /* 可选的LCD非阻塞刷新 */ \
{ Test_ChassisCmd_Log,         200U, 0U }, /* 串口日志 */ \
};
```

验收顺序：

1. 悬空车轮，上电后确认`fault=0`，按KEY1只发送一次1600 cps前进命令。
2. 默认约200 ms后应锁存`fault=3 mask=00`，并看到`owner=0 mode=0`、目标和输出全部归零；触发前`age`应增长到约200 ms。
3. 故障锁存期间再次按KEY1应被拒绝，车轮不得重启。
4. 等待所有启用车轮`|raw|<=100 cps`后按KEY5急停并清故障；若第一次提示车轮未停稳，等待后再按一次。
5. 换回普通`Test_ChassisCmd_Update()`任务，按KEY1运行至少30秒，确认`age`长期约为0～10 ms、`fault=0`且KEY1～KEY5功能正常。
6. 最后回归Motion动作和Basic循迹，确认它们持续刷新速度命令且不会误触发`fault=3`。

该软件看门狗依赖`Chassis_Update()`继续执行；若整个调度器停止，必须依靠另行配置的硬件独立看门狗。

### LCD 底盘速度测试页面

`Test_ChassisCmd_Update()`首次运行时调用`LcdUi_ChassisTestBegin()`激活专用页面，`LCD_Update`负责非阻塞刷新。因此只有任务表同时注册这两个任务时才显示底盘速度测试数据；只注册`LCD_Update`会显示普通仪表盘，灰度校准任务则切换到校准页面。

| LCD 字段 | 含义 |
| --- | --- |
| `MODE` | `STOP`为停止，`SPEED`为速度控制状态 |
| `LIN / TURN` | 当前线速度和转向速度命令，单位 cps |
| `TGT L/R` | 左右侧命令目标速度，单位 cps；斜坡后目标以串口日志`tgt`为准 |
| `FB1 L/R` | 前左 FL、前右 FR 实际编码器速度，单位 cps |
| `ERR1 L/R` | 前轮显示误差，计算为`命令目标 - 实际速度`；斜坡期间控制器实际使用的误差需结合串口`tgt/fb`判断 |
| `PWM1 L/R` | 前左、前右最终PWM输出，已经包含前馈和PI修正，单位为千分比 |
| `FB2 / ERR2 / PWM2` | 仅 4WD 显示后左 RL、后右 RR 数据；当前 2WD 改为显示按键提示 |

LCD 数据页约每 200 ms 更新一次。串口日志继续保留，便于保存完整四轮数据和调参记录。

### （2）按键校准并在 LCD 显示阈值（需要校准时切换）

```c
Task_t task_list[] = { \
{ Test_GPIO_Toggle,              10U, 0U }, /* 运行指示灯 */ \
{ AppTask_BSP_Background,         1U, 0U }, \
{ Key_Update,                    10U, 0U }, \
{ Sensor_Update,                  1U, 0U }, \
{ LineCalibration_Update,       10U, 0U }, \
{ LCD_Update,                    20U, 0U }, \
{ OLED_Update,                   20U, 0U }, \
};
```

使用步骤：

1. 上电后等待灰度传感器在线。因为任务表注册了`LineCalibration_Update()`，LCD/OLED启动页结束后进入`GRAY CALIBRATION`校准页面。
2. 把8路传感器全部放在白底上，等待滤波读数稳定后按KEY1（PE4）；LCD/OLED提示`WHITE CAPTURED`，串口输出`WHITE`和本次八路采样值。
3. 把8路传感器全部放在黑线上，等待滤波读数稳定后按KEY2（PE3）；LCD/OLED提示`BLACK CAPTURED`，串口输出`BLACK`和本次八路采样值。
4. 按KEY3（PE2）计算阈值。LCD显示逐路`TH0`～`TH7`，OLED以两路一行显示`T0`～`T7`，串口同时输出八行`LINE_DETECT_DEFAULT_THRESHOLD_0`～`_7`宏。
5. 若希望下次重新烧录后仍使用这些数值，把串口输出复制到 `Algorithm/line_detect.h`。STM32 运行时不能直接修改电脑上的源文件宏；本次计算值只在当前上电周期内生效。

必须先完成 KEY1 和 KEY2 采样才能按 KEY3；否则串口输出 `GRAY CAL WAIT: PRESS KEY1 AND KEY2 FIRST`。灰度传感器离线时不会记录无效样本。

### （四）字段含义

### 动作库转弯测试说明

`Motion_TurnAngle()`测试要点：

1. 保持车辆静止上电，等待IMU初始化和静止标定完成；若过早按 KEY1/KEY2，动作测试入口会输出 `IMU NOT READY` 并拒绝启动。
2. 第一次悬空车轮按 KEY1，确认左轮目标为负、右轮目标为正；按 KEY2 时方向相反。车轮目标或实际转向方向错误时先检查差速约定、电机和编码器方向；车轮方向正确但日志中的yaw变化方向与命令相反时，再检查`HEADING_IMU_YAW_REVERSE`，不要先改转向参数。
3. 放地面并留出足够空场，分别按 KEY1 和 KEY2。用量角器或地面标线记录实际角度，至少各测3次，分别记录平均角度和重复误差。KEY3/KEY4用于验证500 mm前进/后退，测试时同样留出足够距离。
4. KEY1/KEY2只传入±90°，所有入口统一使用`CONTROL_MOTION_TURN_SPEED_CPS=3000`作为上限。当前比例系数为25.0，90°初始转向命令约为2250 cps；进入±3°容差后停车，连续10个10 ms周期（约100 ms）满足条件才完成，以便继续检查停车后的惯性越界。
5. 若惯性导致越过目标，控制器按角度误差的反方向自动进入500 cps低速回正，并保持低速修正直到重新进入±3°。若回正速度低到电机不动，适当提高`CONTROL_MOTION_TURN_CORRECTION_SPEED_CPS`；若低速回正仍反复跨过目标，则降低该值。

`Test_MotionCmd_Log`字段含义：`st=0/1/2/3`分别为IDLE、RUNNING、DONE、ERROR；`act=0/1/2`分别为NONE、GO_DISTANCE、TURN_ANGLE；`dist=当前/目标毫米`；`yaw`为相对航向角（当前日志取整数）；`tgtL/tgtR`为左右目标cps，越界回正时应看到约`+500/-500`或`-500/+500`；最后四个`out`依次为FL、FR、RL、RR的PWM千分比。动作超过8000 ms未完成会进入`MOTION_ERROR`并停车。

### （四）Basic 丢线恢复测试方法

1. 先悬空车轮按KEY1，确认线路在左时 `RAW<0、OUT T>0`，线路在右时 `RAW>0、OUT T<0`。
2. 正常放在线上和最外侧探头压线时都使用`MODE:TRACK`基础PD；独立`EDGE`模式已经取消，普通循迹输出仍保证`|T|<=L`，内侧轮不会反转。
3. 完全移开黑线：连续2帧后进入`MODE:SEARCH`。线路最后在左时第0阶段应为`P:0 D:1、OUT T:+1000`，线路最后在右时方向相反。
4. 保持丢线：约300 ms后进入`P:1`并反向，转向量约1200 cps；后续依次为`P2：700 ms/1400 cps`、`P3：900 ms/1600 cps`，从`P4`开始保持900 ms/1800 cps并继续交替方向。底盘目标斜坡会让实际轮速变化稍晚于Route的`OUT`命令，属于正常现象。
5. 扫描时重新压到黑线：必须连续识别3帧才回到`MODE:TRACK`；成功后页面保留`R:3`，恢复PD的第一个周期不会使用搜索前旧误差计算微分。
6. 搜索超过约10秒仍未找到线时，应显示`LF:0、MODE:SAFE、OUT L:0 T:0`并停车；诊断状态保持到重新按KEY1或KEY4人工停止。
7. 最后落地回归正常直线、弯道、左右丢线恢复和短白色缺口，确认没有误进入搜索或恢复后突然反向。

所有控制参数只在 `Algorithm/control_config.h` 修改；不要在 Route 或各模块头文件复制一份参数。

## 十一、E220 无线串口双向通信测试

使用以下最简任务表：

```c
Task_t task_list[] = { \
    { Test_GPIO_Toggle,       10U, 0U }, \
    { AppTask_BSP_Background,  1U, 0U }, \
    { Test_E220_Link_Update,  10U, 0U }, \
};
```

两台车可以烧录完全相同的程序。每台车会读取 STM32 芯片唯一编号生成 4 位节点编号，并自动发送以下 ASCII 帧：

```text
E220,1A2B,1
E220,1A2B,2
E220,1A2B,3
```

数字从 1 开始，每成功提交一帧后加 1，发送周期为 1 秒。两台车根据各自芯片唯一编号采用不同的首次发送相位，降低同时发射造成空中碰撞的概率。

`Test_E220_Link_Update()`直接管理本测试的 LCD 和 OLED 页面，不需要再注册`LCD_Update()`、`OLED_Update()`、`Test_LCD_Ascii_Update()`或`Test_OLED_Ascii_Update()`。两块屏幕显示本机节点编号和发送数字、对端节点编号和最新接收数字、有效接收帧数以及链路状态：2.5 秒内收到过有效对端帧显示`LINK:OK`，否则显示`LINK:WAIT`。

两台车的`TX`持续递增、`RX`持续更新且`RX COUNT`增加，能够验证两台车之间的双向无线通信和持续收发稳定性。无线干扰或两端偶然同时发射时允许丢失个别帧；如果长时间保持`LINK:WAIT`，应先检查两端 E220 参数、M0/M1、AUX、交叉接线和各自本地共地，必要时错开时间复位其中一台车。

`AppTask_BSP_Background()`不能省略，它负责推进 E220 的 AUX 忙等待、软件帧队列以及 LCD/OLED 非阻塞驱动。该测试只在`VEHICLE_UART1_LINK_MODE`选择`VEHICLE_UART1_LINK_E220`时收发和显示。

实测结论：两台车烧录同一份程序后，双方均能自动发送递增数字并接收对端数据，LCD/OLED 的`RX`与有效接收帧数持续更新，双向无线通信验证通过。

K210数字识别、快照发送和STM32接收解析已经实测通过。专项测试时先在`BSP/vehicle_config.h`中选择USART1普通直连模式，使日志通过PA9发送到USB-TTL：

```

- `online=1`，断开K210 TX约1秒后变为0，恢复连接后重新变为1。

- `format_err=0`、`overwrite=0`，`check_err`和`snap_err`不持续增长。

```

`Test_StatusLight_Update()`每1秒切换一次状态，顺序为红灯点亮、绿灯点亮、全部熄灭并循环。验收时确认PG5红灯和PG6绿灯与预期一致、切换过程中不会同时点亮、全部熄灭阶段真实熄灭。当前实物已按默认高电平有效配置完成循环测试，结果通过。

测试通过后，正式业务任务表不再注册`Test_StatusLight_Update()`；送药状态机改用`Drv_StatusLight_SetRed()`、`Drv_StatusLight_SetGreen()`和`Drv_StatusLight_Off()`控制。题目要求任何指示灯点亮时小车必须处于停止状态，因此业务代码必须先确认停车，再点亮对应状态灯。
